# 战斗 ECS 与怪物行为树

本设计已实现于 `apps/survivor/src/core/{EntityWorld,CombatWorld,BehaviorTree,EnemyBehavior,CombatSystems,EnemyDefinitions,CombatSimulation,ProjectileBatch,CombatCommand}.ts` 及 `src/worker/`。
应用边界见[应用设计](../app-development.md)，数值与奖励见[战斗合同](combat-and-progression.md)，动作资源见[资产合同](actor-assets.md)。

## 技术选择与接入时机

在扩展怪物攻击前统一实体模型，并直接采用行为树。原有按类型分开的实体池已经采用 SoA，
但数组下标、玩家专用字段与同步删除贯穿战斗和表现；若新行为继续引用这些结构，后续迁移会同时涉及
目标记忆、持续动作、弹道归属、伤害和表现接口。当前尚无存档格式，适合一次完成边界调整。

现在接入的主要成本是统一实体生命周期、改写系统遍历和表现读取，并验证原有成长/装备行为。
地图运行时、地域内容、会话命令和 React 界面结构可以沿用，不需要重新设计整套引擎。
以后接入仍然可行，但若先让技能、状态效果、召唤物和 Boss 行为绑定旧池下标，迁移就会扩散到各功能与测试；
若现在先抽象稳定身份与读写边界来避免该成本，则已经在承担本次 ECS 的主要工作，因此直接完成统一更合适。
这里的收益是数据与系统边界可组合；旧实现本来就是 SoA，不能仅凭采用 ECS 就宣称更快。

| 方案 | 当前收益与代价 | 结论 |
|---|---|---|
| 各实体池继续扩展，之后迁移 | 初期改动少；跨实体行为会增加第二次改写范围 | 不采用 |
| 通用对象 ECS | 组合方便；需要改写现有数组布局并承担逐实体对象与查询成本 | 不采用 |
| 通用 SoA ECS 库 | 可保留数组；仍需约束回收身份、查询修改时机、容量和执行顺序 | 未作为运行时依赖 |
| 应用内有界 SoA ECS | 统一安全整数句柄、固定容量组件和缓存查询；应用显式维护执行顺序 | 已采用 |

bitECS 0.4.0 的发布包验证中，内置版本化 ID 在“回收 A、重用 A、删除 B”的特定排列下，
会将仍然存活的新 A 判为不存在；也不能将含版本位的完整 ID 直接作为固定 TypedArray 下标。
本项目将身份与存储槽明确分开，相关复用排列、超过 32 位的句柄及容量边界有独立测试。
参考 [bitECS 的存储与身份合同](https://github.com/NateTheGreatt/bitECS/blob/main/docs/Intro.md)。

本地 ECS 只提供本游戏使用的创建、销毁、句柄解析与组件交集查询。组件组合在出生时确定；
频繁变化的动作阶段、AI 圈层和冷却是字段值，不通过添加/移除组件表达。
没有通用插件调度器、动态组件注册、序列化框架或过渡用 AI 状态机。

## 数据所有权与实体身份

模拟 Worker 中的 `CombatSimulation` 持有一个 `CombatWorld`，是会话命令、成长、奖励和固定系统执行的入口。
玩家与怪物共享位置、朝向、半径和生命组件；怪物另有出生归属、行为记忆、移动意图及动作时序。
弹道记录阵营、发射者句柄、速度、生命期和发射时的伤害/精英/Boss 数据。
经验与地面物品也是实体；背包、冻结物品定义、地域生成和宝箱消费继续由领域数据管理。

实体总容量为 `1+640+128+768+64=1601`。每种人口上限仍单独检查。
组件按槽存储，查询以固定 TypedArray 保存活跃槽列表，用末项交换删除。
查询游标、存储槽、实体句柄是三个不同概念：游标随交换改变，槽在生命期内稳定，句柄区分槽的不同生命期。

句柄公式为 `(generation-1)×capacity+slot+1`，0 表示无目标；数组只使用 `slot` 索引。
创建时增加该槽代数，销毁时清空有效句柄并归还槽；解析必须同时匹配完整句柄。
代数达到 Uint32 上限后明确拒绝再次创建；支持容量上限保证句柄运算保持安全整数。
怪物卸载/死亡清除出生区块、地域、目标与树运行节点，不保留无限探索历史。

`CombatState.ts` 定义表现需要的字段。核心的 `getRenderState()` 仍借用自己的组件，
只允许 Worker 内的 `RenderFrame.write()` 在完整 tick 提交后读取；主线程不再持有实时 ECS 引用。
`RenderFrame` 将表现字段复制到独立 ArrayBuffer 后转移给主线程；旧表现帧在下一帧接收后才允许归还。
UI 读取独立的低频快照，并在结构化克隆后重新递归冻结。主线程无法通过任一视图修改战斗事实。

## 固定 tick 与结构变更

逻辑固定 120Hz，每 tick 为 1000/120ms，顺序固定：

1. 保存玩家上一位置、推进玩家冷却并应用移动；
2. 同步地域驻留，先卸载失效实体，再生成新驻留人口；
3. 玩家索敌与发射，推进已有弹道，批量结算命中；若玩家死亡立即结束 tick；
4. 自动脉冲收集命中并结算，死亡怪物不再参与本 tick 的行为决策；
5. 怪物感知与行为树、移动执行、攻击时序执行，再批量结算伤害；
6. 玩家存活时处理经验、地面物品、宝箱，以及每 60 tick 的血蓝回复。

行为树决策和怪物动作执行期间不销毁怪物；感知阶段可以先移除已经卸载的实体。
伤害先写入有界缓冲，在其所属阶段之后统一提交。
销毁立即从查询移除；遍历自身查询并删除的驻留、弹道、拾取系统使用“不递增当前游标”的交换删除循环。
创建/销毁不会隐式触发其他系统或重入用户代码。

命中缓冲使用完整句柄。多个弹道同时命中同一怪物时，第一笔致死结算提交一次奖励，其余命中因句柄失效被忽略，
不会伤到复用该槽的经验或物品。结算先后采用明确的系统顺序及查询顺序；相同输入、种子和命令顺序可重放。
同距离索敌以较小句柄破平局；弹道使用线段与圆的最早交点，交点相同也以句柄破平局。

已发射的敌方弹道在施法者死亡或卸载后仍飞行，以发射时的数据造成伤害；反伤只作用于仍然有效的原施法者。
玩家受击保护仍为 0.55 秒，闪避/盾/防御公式不变；致死受击与致死反伤同次结算时仍奖励击杀，玩家保持死亡。

## 共享行为树

树的组合节点为响应式 Sequence 与按优先级选择的 Selector，叶节点为条件和动作。
动作返回 Success、Failure 或 Running；每个实体仅保存一个运行叶节点编号。
连续决策周期续执行同一个 Running 动作，选择另一动作时先 halt 旧动作；前置条件全部失效也会取消运行节点。
树在构建时检查环和空组合节点；定义共享、执行不生成逐怪节点对象、Promise、计时器或每 tick 临时数组。
响应式执行和中断语义参考 [BehaviorTree.CPP](https://behaviortree.dev/docs/guides/asynchronous_nodes/)。

实际优先级：

```text
Selector
  Sequence：没有有效追击目标 → 回出生点
  Sequence：术士未在攻击且目标小于 3.5 → 后退
  Sequence：攻击进行中或进入攻击范围 → 等待冷却/执行攻击
  追击目标
```

内圈且玩家距出生点不超过 14 时才能持有追击目标。离开领地会立即中断攻击并归位。
内圈决策按句柄每 4 tick 错峰（30Hz），保留移动意图，位移和攻击释放仍每 tick 执行。
首次进入内圈、目标丢失/变化、攻击结束立即求值；已成功的空闲叶节点不会因此每 tick 重跑。
中圈一按句柄每 24 tick 错峰更新归位运动（5Hz），中圈二冻结；跨出内圈时在当前 tick 取消攻击，
不会等到下一次低频更新，也不累计补发错过的攻击。中断保留原冷却，并至少等待一次该怪物的后摇时间。

近战锁定前摇开始时的朝向；命中时重新检查玩家是否仍在范围和朝向两侧各 1.1 弧度的扇形中。
普通仆从、斥候、重卫分别为常规挥击、较快拳击、长前摇的大范围重击；斥候追击有轻微侧向摆动。
术士保持施法距离，前摇开始时锁定弹道方向；领主使用三发扇形齐射，不实现生命阶段切换。

| 类型 | 额外近战距离 / 施法距离 | 前摇 tick | 后摇 tick |
|---|---:|---:|---:|
| 地精仆从 | .45 | 44 | 77 |
| 小恶魔斥候 | .35 | 29 | 56 |
| 地精重卫 | 1 | 96 | 120 |
| 小恶魔术士 | 7 | 84 | 156 |
| 裂爪领主 | 9 | 84 | 156 |

定义按秒填写：前摇 .36/.24/.8/.7，后摇 .64/.46/1/1.3，由 `ticksForSeconds` 向上量化到逻辑 tick，误差小于一个 tick。

近战总距离为双方半径加额外距离。术士弹速 4.5，领主 5.5；领主三发相对锁定朝向偏转 `-.24/0/.24` 弧度。
敌方弹道最多 64，总弹道最多 128，保留玩家可用容量。齐射先检查完整容量；不足时本次攻击不发射，仍进入后摇。
弹道存在时间为施法距离除弹速再加 .3 秒；末 tick 只移动剩余生命期对应的距离。

## 表现与验证

动作组件给出种类、锁定朝向和归一化进度；前摇映射到 0–.5，后摇映射到 .5–1。
构建时为四种怪物各增加八帧非循环攻击姿势，运行时继续共享 morph 数据并实例绘制。
近战前摇显示与实际判定角度/半径一致的扇形，施法前摇显示施法者脚下圆环；敌方弹道为红色。
动画与预警只读取模拟结果，暂停不推进动作，取消后清除预警。

测试覆盖身份复用、树抢占、一次命中、锁定方向躲避、圈层中断、弹道最早交点、发射者失效、齐射容量、
重复死亡与同时死亡，以及实际浏览器 morph 权重、预警、弹道颜色和暂停。

`npm run benchmark:app` 单独约束游戏 CPU：真实 24 秒直行战斗，以及 640 怪物加 128 条未命中弹道的满载系统遍历。
每个场景一次预热、五次采样，以每 tick 耗时中位数检查 .5ms / 3ms 预算；报告 Node、CPU 和原始样本。
计时不包含初始化/构建，直行场景拒绝将死亡后的空更新算作工作；满载场景不扣血、不产生死亡，持续保留全部扫描目标。
可用 `--baseline=<独立模块路径>` 对比同种子、同输入的旧版直行场景；攻击规则不同会影响存活人口和击杀数，不能据此单独推算 ECS 开销。
该模块须导出 `CombatSimulation` 和按自身模拟频率实现的 `ticksForSeconds`，确保两侧都测量真实 24 秒玩法时间。
该基准不代表浏览器 GPU 或整帧性能。

ECS 不自动改变地形通行、全局寻路或空间索引。玩家移动与怪物出生仍不检查水体/山地；这些能力需要各自明确的玩法规则与测量。

## 多 Worker 职责与执行协议

已将整个战斗模拟移出主线程。保留一个事实写入者，再将可独立计算且工作量足够的阶段分区，
避免地域对象、PRNG、奖励与生命周期同时受到多个写入者影响。

| 执行者 | 已接管内容 | 写入与提交边界 |
|---|---|---|
| 主线程 | 输入、帧节奏、UI、Three.js 表现、Worker 生命周期 | 提交命令；读取完整快照 |
| 模拟 Worker | 全部 ECS、行为树、移动、攻击时序、伤害、地域人口、成长、背包、随机数 | 唯一事实写入者；串行执行批次与 tick |
| 两个查询 Workers | 达到门槛的弹道线段/圆求交，按弹道区间分区 | 只读取数值快照；只写自己的目标句柄区间 |
| 地图 Workers | 既有地形生成 | 保持地图独立所有权，共享应用线程预算 |

行为树与移动仍在模拟 Worker 中执行：现有最多 640 怪物且外圈降频，这些遍历尚不足以证明逐阶段分发的收益。
伤害与结构变更有强顺序依赖，继续串行提交。背包和成长属于低频领域数据，没有另设线程或强行转成 ECS。
后续真正增加复杂寻路、群体感知或更大规模查询时，可按“只读数值输入 → 分区结果 → 权威提交”增加执行端口；
目前没有未使用的通用任务图、动态系统注册或共享内存锁。

```text
主线程 CombatSession → CombatWorkerClient
  ├─ 有序批次 / 归还旧表现缓冲 → Combat.worker / CombatWorkerHost
  │    ├─ 命令 → 固定 tick 前半段 → ProjectileBatch
  │    ├─ 小批次直接计算；大批次经 MessagePorts 分给两个 Projectile.worker
  │    └─ 等待全部结果 → 原查询顺序结算 → tick 后半段 → 完整快照
  └─ 接收快照 → RenderFrame → CombatLayer / React
```

`CombatWorkerClient` 在主线程创建全部战斗 Workers，再转移 MessagePort 连接模拟与查询端。
因此重开或任何一个 Worker 失败时，主线程能直接终止整组，不依赖嵌套 Worker 随父线程结束。
初始化与推进共用连续请求序号；每次只允许一个未完成请求，乱序和重入明确失败。
每批最多 30 tick、64 条命令，所有命令按收到顺序在该批 tick 之前执行；查询等待期间不处理下一条命令。

主线程再保留至多 30 个待执行 tick 与 64 条待提交命令，使用最新移动输入处理待执行 tick。
超过 tick 上限的墙钟积压丢弃并计数，命令溢出则失败；每批是确定的模拟输入，不承诺不同帧节奏下的原始键盘事件完全等价。
暂停丢弃尚未发送的 tick，已发送批次允许提交，随后用零 tick 请求确认最终快照；隐藏不积累后台追赶时间。
Worker 按批次发布表现，每 12 tick（10Hz）发布常规 UI 快照；初始化、命令、通知、死亡和零 tick 请求强制带回 UI 快照。
表现用收到时刻到下一 tick 的时间对前后位置插值并钳制，不外推未知位置。

### 渲染隔离与扩展边界

`bootstrap`、`CombatSession`、`HexMap.animate`、`CombatLayer` 与 Worker 协议共同保证模拟计算与主线程执行分开、
状态由单一线程写入、队列和内存有界；不保证 Worker 负载对帧率没有影响。

| 情况 | 当前行为与限制 |
|---|---|
| 模拟或查询很慢 | `CombatSession.frame` 不等待推进 Promise，地图继续绘制最近完整结果；一个逻辑 tick 的插值钳制后角色停在已知位置，输入到表现的延迟增加 |
| 查询结果未齐 | 模拟在 `Promise.all` 处等待所有弹道分区，后续 tick 与命令不能越过该结算阶段；只阻塞模拟进度，不同步阻塞主线程 |
| 跨线程修改状态 | 活跃 ECS 留在模拟端，表现缓冲转移后发送端失去访问权；查询端只有数值副本，不持有场景对象或权威组件 |
| 错误的业务结果 | 序号、缓冲大小、查询计数与输入坐标等已有边界检查，但不会逐项证明所有输出字段的业务正确性；错误坐标或动作仍可能通过合法消息影响表现 |
| 结果返回主线程 | TypedArray 视图绑定、UI 快照冻结/发布、实例矩阵与动画数据更新、地形挂载和 GPU 上传仍有主线程成本 |
| 多线程资源竞争 | 固定线程数限制并发数量，不为主线程保留独占 CPU 核或内存带宽，也不保证任务时延 |
| 战斗 Worker 失败 | 主线程主动终止整组战斗 Workers 并进入 failed；这是一致性策略，不是继续维持正常战斗的故障隔离 |

主线程只有地图拥有的 RAF 循环：`beforeframe` 调用 `CombatSession.frame`，依次采样输入、提交有限批次、
更新角色表现与跟随镜头；地图随后更新控制器、流送和场景，发出原有绘制前 `frame` 事件，再提交绘制。
`afterframe` 才采集本次主循环耗时并发布诊断。初始化也等待该帧入口更新角色，不再单独触发表现更新。
`bootstrap` 注册/释放帧监听和长帧观察器，不创建第二个 RAF；关闭时先移除监听，再释放会话与地图。
地图恢复 WebGL 上下文后首帧 `dtS=0` 会重建游戏时钟和诊断窗口，不追赶失去绘制上下文期间的时间。
`afterframe.cpuFrameMs` 包含战斗表现和地图/Three.js 工作；`frame.cpuFrameMs` 仍表示前一主循环耗时。
异步消息、React 更新、浏览器布局和最终屏幕呈现并不全部落在主循环计时内，因此同时观察帧间隔与浏览器长帧。
地图挂载已有 `FrameTaskScheduler`，但时间预算只在任务之间检查，不能抢占一个已经开始的长任务；
游戏适配器当前关闭 `adaptiveStreaming`，使用固定流送设置。两者均不能作为严格的整帧耗时上界。

当前 640 怪物、128 弹道等容量是已实现的存储/人口边界；Node 基准和软件渲染 E2E 不构成目标设备上的帧率承诺。
增加内容种类与增加同屏工作量需要分别评估：技能、状态效果、Boss 阶段可以在现有权威端增加领域系统，
由 `CombatSimulation` 明确编排提交顺序；寻路/群体感知需要只读任务输入与结果有效性规则；
成倍增加人口会同时影响全量表现复制、当前弹道逐怪扫描、实例动画更新和 GPU 成本，不能只增加 Worker 数量。
地形通行尚未进入战斗规则，接入寻路前需要明确地图与模拟共享的通行数据及版本，不能由 AI 读取 Three.js 场景作为事实。

保留当前单一事实写入者与有界数值任务的骨架；空间索引、快照布局调整或新增并行阶段的优先级，
由代表性实机场景与具体功能的工作量决定。下述提交入口已经接入模拟；具体寻路算法、通行数据和独立渲染 Worker 尚未实现。
Worker 上下文与转移所有权的浏览器语义见 [MDN Worker](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Using_web_workers)
与 [MDN 转移对象](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Transferable_objects)。

### 必须完成与可延后任务

`SimulationTasks` 是每局权威端拥有的提交边界，不创建线程或通用任务图。
当前弹道推进通过 `tasks.require()`，该屏障包含命中提交与 tick 后半段；期间拒绝进入下一 tick 或提交延后结果。
查询执行器沿用独立 MessagePorts、容量和超时约束，所有命中仍在本 tick 内确定并按原顺序结算。

`tasks.submit({ key, entity, maxAgeTicks, execute, commit })` 返回请求标记或容量不足的 `undefined`，不返回可等待的结果 Promise。
执行器捕获只读输入并负责派发计算、响应 AbortSignal 和传输超时；其完成回调只将结果放入收件箱。
标记含请求编号、任务键、完整实体句柄、发出 tick 和 `worldRevision`；当前世界版本来自 `RegionalWorld` 的驻留变化。
每个 tick 在同步地域/实体驻留后、武器和攻击计算前调用 `commitReady`，按请求顺序提交已完成且仍有效的结果。
相同实体/任务键采用最新获准请求；实体死亡或槽复用、驻留版本变化、超过 tick 寿命都会取消并丢弃旧结果。
提交函数必须同步返回 `undefined`，并收到实际提交 tick；提交期间拒绝重新进入 tick 或另一个提交阶段。
完成一个 Promise 本身不允许成为异步的世界写入入口。

每局最多 64 个未释放任务，已取消但执行器尚未结束的任务仍占容量，防止重复请求制造无界后台队列。
当前任务执行失败在下一提交边界抛出并由会话失败流程处理；过期任务的失败不会污染新请求。
重开/关闭时释放整个收件箱并中止任务；没有延后任务时该入口不增加 Worker 或额外后台计算。
现有怪物行为没有为了使用接口而人工异步化；之后的寻路需要接入真实通行数据及其版本，不能把驻留版本当作通行数据版本。
未来让异步结果影响玩法时，重放必须记录接受的任务结果与实际提交 tick；仅相同种子和输入不保证不同完成时序下的行为相同。
当前玩法未消费延后任务，既有逐 tick 输入重放合同保持成立。

### 缓冲与确定性

`ProjectileBatch` 大小固定为 27,696 字节，包含玩家、最多 640 怪物和 128 弹道的数值输入及目标句柄输出。
每个查询 Worker 只有一个循环转移缓冲；连续弹道区间按估算求交次数平分，避免友方与敌方弹道混合时工作量偏斜。
它们不读取地域对象、不消耗随机数、不创建或删除实体。
模拟先收集全部弹道的起止位置，记下槽到批次游标的映射；所有区间完成后，再按原查询的交换删除顺序提交命中，
保持奖励与随机数消费顺序。平局仍比较完整句柄。线程完成顺序不会改变结果。

表现缓冲每份 174,957 字节，共两份：初始模拟端与主线程各持一份，收到新帧后，下一请求才归还旧帧。
只传表现需要的字段，生命事实、行为树记忆、冷却、地域引用和物品定义留在权威端。
初始分配后不逐帧新建大缓冲；每次转移会重新绑定 TypedArray 视图。50 批/秒时表现复制约 8.75 MB/s，
该数值不含低频对象快照和浏览器消息调度开销。

使用 transferable ArrayBuffer 明确转移所有权，发送端的对应缓冲会 detach；活跃 ECS 的组件存储永不转移。
当前无需 SharedArrayBuffer；后者需要跨源隔离，并且仍需定义发布与同步协议。
参考 [MDN 转移对象](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Transferable_objects)、
[共享内存约束](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/SharedArrayBuffer)。
入口使用 Vite 可识别的 `new Worker(new URL(..., import.meta.url), { type: "module" })`，生产构建输出独立 Worker 文件。

### 预算、测量与失败

`WorkerBudget` 按浏览器报告的逻辑核数给出固定预算：1–5 核为 1 地形 + 1 模拟；6–7 核为 2 地形 + 1 模拟；
8 核以上再分配 2 查询，最多 5 个后台 Worker。小核数仍由专用模拟 Worker 执行，不回到主线程。
单独增加一个查询 Worker 只会增加等待和通信，当前没有与之重叠的权威工作，因此不分配单查询线程。

工作量估计为每条友方弹道的怪物数之和，加每条敌方弹道的一次玩家检查。
只有配置了查询线程且估计至少 49,152 次求交时才分发。这里选择的是执行粒度，任何线程失败都不会切换计算路径继续旧局。
2026-09-09 在 Windows / Node 22 / i7-11700K 的试测中，640×32 检查串行为约 .085ms，
双线程含拷贝、转移和等待约 .131ms；640×128 则约 .429ms 对 .305ms。
因此门槛高于小批次和收益较窄的 640×64；这不是浏览器端提速保证，也不说明日常战斗已经需要并行碰撞。
`npm run benchmark:app:workers` 可复测当前调度策略，原始样本与缓冲尺寸见[测量记录](./measurements/workers-node.json)。
该记录的最终复测满载中位数约为 .343ms / .312ms，说明收益会随运行与 JIT 状态变化，不能把试测比例当作稳定提速承诺。
真实浏览器 E2E 另外强制满载，验证独立 Worker 确实参与查询；软件渲染测试不承担帧率证明。

请求和查询都有 15 秒超时；创建失败、脚本错误、解码失败、非法协议、超时均进入 failed，
终止全部战斗 Workers，拒绝等待请求并清空队列。加载世代同时防止旧结果与旧错误覆盖新局。
重开复用地图资源但新建战斗模拟与线程；重试失败局也是重新初始化，不延续部分提交状态。
`session.diagnostics` 暴露存活线程数、在途请求、积压/丢弃 tick、命令数、批次耗时、传输往返时间和本地/并行批次数。
测试覆盖真实线程数值一致性、交换删除后的命中顺序、缓冲 detach 与复用、超时、命令顺序、背压、暂停和旧结果失效；
浏览器再验证 20 次重开、查询线程崩溃、重新加载和关闭后的线程数归零。

### 逐 Worker 负载观测

左上 `WorkerLoadPanel` 展示模拟、各碰撞查询和各地形 Worker，使用任务占用率而非 OS CPU 利用率。
`TaskActivity` 在请求发出和回复到达处累计墙钟耗时；模拟记录主线程到模拟 Worker 的往返，
查询记录模拟 Worker 到对应查询 Worker 的往返。客户端已有完成数和往返耗时复用这份计数。
两者均包含通信、等待及调度延迟，不能相加推导 CPU 核利用率。
模拟等待查询时也处于占用状态。查询统计随完整战斗批次回传，不额外向 Worker 发送轮询请求。
一次模拟任务指一个请求批次，查询任务指一个弹道分区，地形任务指一次生成请求；任务频率不等同于模拟 tick 频率。

地形侧 `WorldGeneratorPool.workerActivity` 独立提供每个线程的 ID、在途状态、累计占用毫秒、
已结束任务数、最近耗时及当前任务类型，`HexMap.workerActivity` 只读转发当前世界的数据。
统计只覆盖实际发给线程的任务，不计排队等待；已发出的任务即使取消，也统计直到其执行 Promise 结束。
线程替换获得新 ID 并清零，销毁后列表为空；静态世界不产生虚构的地形线程。

`WorkerLoadSampler` 约每秒通过已有帧循环取一次值，按实际经过时间计算
`占用率 = Δ累计占用毫秒 / Δ墙钟毫秒`、`任务频率 = Δ结束任务数 / Δ墙钟秒数`。
模拟与地形记录包含当前在途时间，因此长任务尚未回复也能显示占用；查询记录在批次完成时归入采样窗口。
延迟回传跨越多个窗口时百分比钳制到 100%，不会显示超过单线程容量的值。
首次采样和计数器重置只建立基线；每个活跃线程只保存一份基线，没有无界历史。
暂停后的空闲窗口归零；死亡后也继续观察地形线程。重新加载或重开重建采样基线，避免旧局影响新局。
地形任务计数包括失败或取消后结束的请求；战斗异常时仍按既定失败流程终止战斗 Workers，负载面板不参与调度。

### 帧、阶段耗时与输入反馈

`FramePerformance` 在 `afterframe` 记录采样，约每秒与 Worker 行一起发布，暂停后仍继续；加载、隐藏/恢复和重开重置窗口。
面板标明实际窗口秒数，主线程卡顿时不把变长的采样窗口仍称为一秒；恢复时同时重建 Worker 占用基线。
窗口均值累计所有样本，P95 使用窗口内最近最多 512 个值，TypedArray 复用，仅发布时排序；不保存无限历史。

| 指标 | 实际口径 |
|---|---|
| FPS / 帧间隔 P95 | 根据相邻主循环的 RAF 时间戳计算；隐藏/恢复后的首个间隔不参与 |
| 主循环 CPU / P95 | 从地图帧开始到 Three.js 绘制提交完成，包含输入、角色、镜头和地图工作；是墙钟耗时，不是 OS CPU 利用率 |
| 角色 / 镜头、地图挂载 | 分别计时 `HexCombatView.render` 与地图帧任务队列，前者包含实例动画更新 |
| 收包 / UI 发布 | 主线程协议处理、绑定表现视图、冻结快照和同步发布；不包含之后的异步 React 渲染 |
| GPU | 复用地图的异步 WebGL 查询，只统计新完成的样本，并保留样本年龄；没有可用样本时显示 — |
| 浏览器长帧 | 可用时观察 `long-animation-frame`，记录窗口计数、最长帧、最大阻塞和从样式/布局开始到帧结束的最长渲染尾段；只覆盖超过 50ms 的页面帧 |
| 快照年龄 | 距离收到最近完整模拟结果的墙钟时间，暂停时明确标记并允许继续增长 |
| 采样→绘制 | 最近一次移动输入变化，从主线程采样到采用该输入的结果完成 Three.js 绘制提交；含积压与往返，不含设备、事件排队和屏幕呈现 |
| 模拟执行 / 查询等待 | `batchMs` 为模拟端处理整批的墙钟时间，`queryWaitMs` 为远程查询 join 等待之和，`executeMs = batchMs - queryWaitMs`；执行段也不是系统 CPU 计数 |
| 通信 / 调度 | 主线程往返减去 Worker 批次耗时，包含消息克隆、线程调度和主线程接收排队，不能解释为纯通信成本 |
| 积压 / 丢弃 tick、延后任务 | 显示在途批次、待执行 tick、局内因队列溢出丢弃的 tick，以及延后任务在途数与累计失效数 |
| 超出追赶上限 | `FixedStepClock` 报告帧间隔超过 250ms 追赶上限而裁掉的时间，会话按局累计；与队列溢出分开，暂停、隐藏和上下文恢复不计入 |

输入反馈只在实际绘制后确认，同一输入不会每帧重复计时；暂停、隐藏和新局不会接纳旧输入的迟到确认。
浏览器长帧观察器按应用生命周期创建一次，重置之前/加载期条目丢弃，关闭时 disconnect；不支持时明确缺少观测，不伪造零值。
GPU 和长帧记录异步送达，按到达窗口统计，不能与当前帧 CPU 耗时逐帧相加。
长帧机制见 [Chrome Long Animation Frames](https://developer.chrome.com/docs/web-platform/long-animation-frames)。
这些指标组合定位 Worker 等待、主线程工作和页面卡顿，仍不等同于全线程 CPU 采样或实机性能验收。

### 固定频率配置与吞吐估算

`GameConfig.ts` 统一定义目标、预算、背包规则和品质色，派生周期不重复写常量。运行期不修改固定步长。
固定逻辑与渲染刷新分开；固定更新不代表主流引擎统一使用 120Hz，参见 [Unity 固定更新](https://docs.unity.cn/6000.0/Documentation/Manual/fixed-updates.html)。

| 工作 | 当前调度 | 说明 |
|---|---|---|
| 权威模拟、移动、弹道、命中 | 120Hz 固定 tick | 每 tick 8.333…ms；一秒的渲染帧增加不额外生成逻辑时间 |
| 近圈行为决策 | 30Hz，按句柄错峰 | 位移和攻击释放不降频；目标失效与驻留变更立即响应 |
| 远圈归位 | 5Hz，按句柄错峰 | 0.2 秒位移合并，静态圈不推进 |
| 回复 | 2Hz | 保留每半秒回复量 |
| UI 完整快照 | 10Hz | 命令、通知、死亡和屏障可强制发布 |
| 碰撞 Workers | 按 tick 的查询需求 | 达到 49,152 对检查才派发；无独立空转定时器 |
| 地形 Workers | 按流送需求 | 沿用地图调度、并发和挂载预算，不伪造固定 FPS |
| 主线程绘制 / 诊断 | 浏览器 RAF / 约 1 秒 | 绘制使用最新完整结果；诊断按实际窗口统计 |

`FixedStepClock` 用整数微秒×Hz 累加，再除以一百万取得 tick，避免把 120Hz 周期取整造成长期漂移。
单帧接受最多 250ms，因此批次和待执行队列上限都派生为 30 tick；暂停、隐藏、上下文恢复不补算间隔。
这限制积压并保证玩法时间步长，不能保证慢设备持续达到 120 个已完成 tick/s。

Worker 记录本批实际执行的 tick 数和单独的模拟阶段时间（包含查询等待，排除命令与快照打包）。
主线程按窗口累加，不对多个批次的 Hz 作简单平均：

- 逻辑实际 Hz = 已完成 tick 数 / 实际窗口秒数，批次跨窗口到达会产生波动。
- 每 tick 耗时 = 完整模拟时间之和 / 已完成 tick 数；执行段另扣除查询等待。
- 预计逻辑上限 = 1000 / 每 tick 耗时，逻辑预算占比 = 每 tick 耗时 / 8.333…ms。
- 理论 FPS = 1000 / max(主循环均值 + 每帧均摊的收包/UI 发布耗时, GPU 均值)。CPU/GPU 两条流水线不相加。

没有 GPU 样本时标注“理论 FPS · CPU”，不能解释成整机渲染上限。估算不包含全部异步 React、页面布局、设备呈现和系统竞争，
与实际 FPS、长帧、快照年龄一起判断。零 tick 批次和暂停窗口不产生逻辑吞吐估计，也不会用初始化耗时倒推逻辑频率。
理论值不会反过来加速逻辑；用户可以观察新增功能是否提高每 tick/每帧成本，即使实际刷新率暂时仍受目标频率限制。
