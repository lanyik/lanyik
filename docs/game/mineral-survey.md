# 矿藏生成与登陆勘察

状态：已实现三类矿藏、逐格初始储量、分块显示、矿点查询、矿区定位和起步区域筛选。
开采、库存与建筑放置见 [基地建造与采矿](./construction-and-mining.md)，游戏存档尚未实现。
勘察报告显示初始矿量，选中矿格或采矿机显示实时余量；实际库存单独展示。
总体方向见 [App 开发设计](../app-development.md)，会话与时钟见 [应用入口](./application-shell.md)。

## 内容范围

本轮采用三类可采矿藏，覆盖首个 30–60 分钟原型的建材、机械和基础电子链。
木材来自现有森林，水属于环境供给；两者不作为额外矿种。

| ID | 名称 | 用途方向 | 单格初始储量 | 登陆区可达储量下限 |
|---|---|---|---|---|
| `iron` | 铁矿 | 铁材、结构件、机械部件 | 2,000–6,000 | 12,000 |
| `copper` | 铜矿 | 铜材、基础电路 | 1,500–5,000 | 8,000 |
| `stone` | 石材 | 建材块、地基 | 3,000–8,000 | 12,000 |

内容入口为 [minerals.ts](../../apps/expedition/src/content/minerals.ts)。以上是原型参数，
需要在真实采集速度、施工成本与配方接入后平衡。开局不要求煤炭、石英、原油或稀有矿，
这些原料在对应合金、精密电子、化工与巨构工艺实现时再进入内容和阶段可达性检查。

## 确定性生成与身份

[MineralField](../../apps/expedition/src/core/resources/MineralField.ts) 是无缓存的纯数据
生成器，不导入 Three.js、React 或 DOM。它不修改 `TileInfo`、地形编码或 Worker 协议。

矿藏生成版本为 1。全局坐标按 `16×16` 地质区域划分，区域哈希由种子、生成版本和
完整坐标字组成。每个区域有 20% 概率为空，其余区域生成一个矿体；铁、铜、石的权重
为 `4:3:3`。中心可位于区域边缘，两个轴的半径为 `2.5–4.833…` 格，边界由椭圆判定。
查询一格时检查其周围九个地质区域，重叠时选择中心强度最大的矿体；同强度按固定遍历
顺序决定。地质区域与地图 source/render chunk 的大小无关。

海洋、近岸水域和湖泊格不生成矿点；其他干地可以有矿。地形和河湖判定来自现有生成器
的最终格子数据，地貌不会被矿藏生成器改写。森林状态变化不改变已有矿点身份或储量。
矿体中心强度和逐格哈希共同决定储量，结果始终是内容范围内的正安全整数。

| 数据 | 定义与所有权 |
|---|---|
| `depositId` | `m1:区域X:区域Y`，标识矿体 |
| `id` | `depositId:格X:格Y`，标识可开采的格子 |
| 世界身份 | 使用完整世界 descriptor；局部矿点 ID 只在该世界及矿藏版本内唯一 |
| `initialAmount` | 可重建的初始矿量，随只读 `MineralNode` 发布 |
| 已开采量 | `Industry` 持有按矿点 ID 记录的实际开采增量；不能存入模型实例或地形标记 |

负坐标使用向下取整，不以访问次序、渲染驻留、墙钟或 `Math.random()` 决定结果。
重新勘察相同世界会重建相同矿点。初始矿藏减去实际开采增量决定余量；模型卸载、
重新查询和拆除采矿机都不会补回已采资源。当前重新勘察代表开始新游戏，会清空旧的
建筑、库存和开采增量；跨页面恢复待游戏存档接入。

## 有界勘察与可达性

[surveyTerrain.ts](../../apps/expedition/src/adapters/surveyTerrain.ts) 使用公开
`WorldBaseChunkSource.sampleBaseChunk()` 取得地形，按公开解码函数转换为纯数据窗口。
采样不安装 source chunk，不挂载地形、树林或矿石模型。

勘察依次检查原点及周边八个固定区域，区域中心沿两个轴相隔 96 格。每个窗口为
`96×96`，当前 source chunk 为 `24×24`，一个窗口包含 16 次区块采样；同时最多提交
4 个请求。最多检查 9 个窗口，完成后保留选中区域的只读报告和地形窗口；适配器缓存
这个窗口的只读地块与矿点，供建造和连通检查读取。每个窗口检查中心附近
25 个候选点，按距窗口中心的距离及固定坐标顺序排列。

[LandingSurveyWindow](../../apps/expedition/src/scenarios/landingSurvey.ts) 复用基建公开的
六边形邻接规则，以广度优先搜索核对地表路径。当前勘察车辆可以经过干燥的普通地形、
丘陵和林地，不能穿过海洋、近岸水域、湖泊或山地。初始勘察不包含建筑；建造后的
基地服务检查在同一地形窗口上叠加实际建筑占地，布局变化立即重算连通。道路尚未实现。

| 检查项 | 当前门槛 |
|---|---|
| 指挥中心周边空地 | 半径 2 的完整 19 格均为普通平原，无丘陵、森林、湖泊和矿点 |
| 连片建设用地 | 从中心沿可建设格移动 8 步以内至少 60 格，同样排除林地与矿点 |
| 起步林地 | 从中心沿可通行地表移动 18 步以内至少 8 格森林；尚不换算木材产量 |
| 起步矿藏 | 18 步内可到达的采集作业位置满足上表三种储量下限 |
| 第二片矿区 | 19–32 步内可达的铁或铜矿，矿体身份不属于任何起步矿体 |

矿点可以位于可通行格，也可以位于其相邻的干燥山地资源端；当前 `1×2` 采矿机将
资源端放在矿格，作业端放在相邻可建平地。距离按到作业位置的最短地表步数计，同一矿格被多个邻格触达时
只计量一次。起步范围统计所有符合条件的矿格；报告保存总量、格数和最近矿点。

窗口内找到首个通过全部检查的位置后发布推荐登陆区。检查失败返回空地、建设用地、
林地、矿量或扩张矿区不足的原因；全部候选失败后结束此次勘察，界面允许用户另选种子。
这表示本次有限勘察没有找到合格位置，不表示整颗无限星球不存在可用地点。不会自动
更换种子、追加无界搜索、抹平地形或补刷必需资源。

推荐登陆区需要玩家手动放置指挥中心，多格占地和基地服务路径已按建造合同校验。
玩家另选指挥中心位置时，不重新执行整套起步资源筛选。供水、可采样生物、后期原料
和配方闭包检查仍按后续阶段实现。

## 加载、查询与渲染

[HexWorldView](../../apps/expedition/src/adapters/HexWorldView.ts) 在勘察阶段拥有新建的
procedural source 和取消信号。新请求或退出会取消勘察并释放尚未移交的 source；失败也
释放它。勘察成功后以推荐位置调用 `HexMap.loadWorld()`，由地图接管该 source。
过期加载不能发布到当前会话，只有勘察和地图加载都成功后才进入 `ready`。

[GameSession](../../apps/expedition/src/app/GameSession.ts) 发布只读勘察报告和包含矿点的
地块快照。`focus-survey` 命令可定位铁、铜、石、推荐登陆区和第二片矿区，只移动镜头，
不修改时间或储量。实际点击地块后显示矿种、单格剩余储量和用途；新勘察清除旧报告与选中。

[MineralLayer](../../apps/expedition/src/presentation/layers/MineralLayer.ts) 通过公开
`WorldRenderLayer` 接入。source chunk 挂载时计算矿格，按现有 `12×12` render chunk
分组，每组使用一个 `InstancedMesh`；同一种共享岩石几何体用颜色区分矿种，每格显示
四块低面数矿石。它们是矿藏的表现，矿量不保存在实例缓冲中。
矿点耗尽时，会话提交耗尽 ID 集合，受影响的实例缩放归零；保留固定缓冲容量，避免
反复分配。淘汰后重新显示仍按耗尽集合构建，不会把已经采完的矿石重新画出。

共享几何体由独立资源账户持有；每组实例矩阵和颜色缓冲由区块调度器计费，在首次可见
时创建。GPU 淘汰释放实例上传，CPU 淘汰清空实例缓冲；再次可见时重建。共享岩石不会
因为某组不可见而被反复销毁。矿石贴合公开地表高度，在地表高度变化时更新位置与
包围盒；卸载移除对象，最终退出释放几何体、材质和账户。
